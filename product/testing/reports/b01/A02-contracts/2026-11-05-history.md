## Frozen public boundary

| Method and path | Request | Response |
| --- | --- | --- |
| GET `/api/conversations` | `ConversationListRequest` (empty query) | `ConversationListResponse { conversations }` |
| POST `/api/conversations` | `ConversationCreateRequest` (empty body) | `ConversationDetail` |
| GET `/api/conversations/{conversation_id}` | `ConversationRequest` (decoded path ID) | `ConversationDetail` |
| POST `/api/conversations/{conversation_id}/messages` | Path `ConversationRequest`, body `ConversationSendRequest { message }` | `ConversationSendResponse { conversation, messages: [user, assistant] }` |

`ConversationSummary` contains stable `conversation_id`, `title`, `created_at`, `updated_at`. IDs are opaque, path-safe ASCII segments of 1–128 characters, starting with a letter/digit and then letters/digits/underscore/hyphen; M15 generates them and does not reuse them. Server timestamps are aware UTC. Sort the list by updated time descending, breaking ties by conversation ID ascending. Create an empty thread titled `New chat`; derive its title once from the first user message by collapsing whitespace and taking the first 80 Unicode code points. No title model call. New/list/read work without an API key. Unknown IDs are `not_found`, never silently created; invalid input uses `invalid_request`, unavailable chat uses `missing_key`, provider failures use `provider_error`, and unreadable/corrupt disk state must surface an error without resetting/overwriting it.

`ConversationDetail { conversation, messages }` returns **all** saved messages. Every saved user/assistant message has a stable ID, explicit role and server timestamp. User text is retained in full; blank sends are rejected. Saved assistant messages embed the complete existing `ChatResponse`, preserving text, fact/source citations, markers, attachments/layout/highlights/URLs, warnings and observation. Its conversation ID must equal the owning thread. A successful send returns the updated summary and exactly its two committed messages, so M18 can append them and update the list without replacing prior history. Existing `ChatResponse` fixture shape is preserved; its optional ID remains valid outside a saved-message envelope.

`POST /api/chat` retains `ChatRequest -> ChatResponse` for compatibility. Its optional conversation ID selects the server thread, and an absent ID creates a new one. Its existing client `history` remains parseable but **must be ignored** for both model context and citation authorization. M03 adapts this route to the same M15 service and returns `send_result.messages[1].response`. It must not maintain another history or ledger.

## Server state, model window and composition

`ConversationState { schema_version: "chat-history/v1", detail, ledger }` is a server-only disk schema. `ConversationLedger { conversation_id, entries }` keeps the full log of successful actual tool returns, with tool call ID, owning saved user-message ID, tool name, arguments and typed full result. The ledger owner must equal the history owner, call IDs are unique within the thread, result types match the named tool, and call owners must exist among that thread's saved user messages. Read/send payloads expose no ledger; new send requests accept no history/facts/results/ledger. Shape validation alone cannot establish that tool results were honestly produced: M15 must load only its own store and record actual tool executions.

M15 rebuilds citation authorization solely from the selected thread's retained tool returns (latest returned value per fact name). Neither assistant claims nor client history authorize a fact. Do not merge global or other-thread state. Reset unique-match attachment fallback each send. Retain full saved messages and full ledger after reload/restart, including tool evidence older than the model window. A01 alone configures/ignores `development/chat_history/`; M15 owns atomic file writes and bounded per-conversation serialization in its existing `backend/app/chat.py`. Preserve already saved user messages/tool results on errors; do not invent a successful assistant reply or overwrite corrupt history. No database or extra application module.

`ConversationContext { conversation_id, turns }` is a separate server-only projection, with **at most 10 individual user/assistant messages including the current user message**. It is the tail of selected saved message text plus the current user message; do not append the current message twice. Pass only those turns to Luna alongside system instructions and the current tool exchange. Never use a provider session/previous response ID that reintroduces omitted or other-thread history. Full disk/read history has no 10-message limit. Luna remains `gpt-6-luna` only.

M03 receives one `ConversationService` implementing synchronous `list_conversations(request)`, `create_conversation(request)`, `read_conversation(request)` and asynchronous `send(path, body)`. M15 exports `create_chat_service(*, history_dir: Path, tools: FactTools, client: object | None) -> ConversationService`, as frozen by `ConversationServiceFactory`. M03 supplies A01's resolved directory, M14's real tools and the private OpenAI Responses client, or `None` without a key. No SDK, storage or router imports were added to contracts. The TypeScript service mirror uses a string path and Promise for send; it is not an API exposing disk/client state.
