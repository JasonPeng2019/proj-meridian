## Implemented boundary

Only `development/backend/app/chat.py`, this report, its static receipt and
`testing/tests/test_chat_history.py` belong to this slice. No existing contract,
config, router, UI, documentation, USER_TODO, tool or source file was changed.
No local suite, dependency install, build, server, browser, PDF/CAD work, key read,
provider call, prep CLI, delegated agent or real user history was executed/created.
No new human decision is needed for this slice.

- `ConversationStore` writes one `conversation-<opaque-id>.json` per thread using
  the unchanged `ConversationState` schema. Same-directory temporary write,
  flush/fsync and `os.replace` preserve the complete detail and private ledger.
  Reads reload disk. Persistent per-thread OS locks work across store instances
  and processes; wait is bounded to five seconds by default, returning a
  retryable `stale_conflict` rather than an unbounded wait. Different threads have
  distinct locks. No database, storage module, global ledger or lock registry.
- IDs are server UUID-based safe segments; titles start as `New chat`, derive
  once from the first full user message by whitespace collapse/80 code points,
  and remain stable. UTC timestamps advance monotonically per thread; list order
  is updated descending, then ID ascending on ties.
- Public list/create/read use exactly the frozen request/response types. Read
  returns all messages and complete assistant payloads, including raw text,
  facts/sources, citation markers, attachments/highlights/URLs, warnings and usage
  observations. The private ledger and storage paths are absent from public
  models/errors. Unknown IDs fail `not_found`; malformed inputs fail
  `invalid_request`. Corrupt/schema-invalid/misowned files, duplicate JSON fields,
  non-JSON constants and file/lock symlinks fail without replacing the history.
  Listing surfaces corrupt entries and unreadable directories rather than
  silently returning an empty list. Interrupted temporary files are not history.
- Server-only `read_context(path, body)` and `thread.context(body)` project saved
  user/assistant text plus the current unsaved user, once, then take the last ten
  individual messages. They do not save/truncate history, use another thread,
  call tools or a model, or authorize citations from assistant/client text.
- Server-only `server_thread(path)` yields an active `ConversationWriter`.
  `append_user`, `record_tool`, `append_assistant` commit separately under that
  same lock, retaining saved user/tool work if a later provider step fails.
  Replies must belong to the selected thread; tool entries must reference its
  current saved user and have unique call IDs. Detached snapshots cannot mutate
  the store, and an escaped writer cannot append after releasing its lock.
  This boundary accepts trusted server output; schema validation does not prove
  tool execution or grounded citations. Those remain B06's responsibilities.

## Exact A03 / B06 integration

The frozen factory is exported unchanged:

```python
create_chat_service(*, history_dir: Path, tools: FactTools, client: object | None) -> ConversationService
```

A03 passes `Settings.chat_history_dir`. No settings/key loading occurs here.
The early factory never accesses tools/client, including when a client is supplied.
Before M14 exists, A03 may instantiate `ChatService(settings.chat_history_dir)`
directly for history-only wiring without inventing a tool implementation.
`list_conversations`, `create_conversation`, `read_conversation` are synchronous;
`send(path, body)` is asynchronous. A03 catches `ChatServiceError` and returns
`error.response` (frozen `ErrorResponse`) with `error.status_code`.

`ChatService.send_available` is **False**. A valid known-thread send raises
`unsupported` / HTTP 501 with an explicit B06-unavailable message, creates no
assistant/user message and never accesses tools/client. Invalid or unknown/corrupt
threads still fail plainly. A03 must retain this unavailable capability honestly
even when a key/client exists; key presence alone does not implement sending.

B06 must implement the actual Luna-only Responses loop, system instructions,
bounded provider/tool work, genuine usage/error recording, latest-returned fact
index from only the selected private ledger, citation/Undetermined parsing,
warnings and attachment selection from the same validated trace. No such behavior
is claimed here. B06 should hold one `server_thread` across its exchange, obtain
`thread.context(body)` **before** `append_user(body)`, record each actual successful
tool return using that saved user ID, and append its validated owning-thread reply.
Do not nest store reads under this non-reentrant writer lock. Run blocking store
work off the async route event loop. Return the frozen two-message
`ConversationSendResponse` after successful persistence. Preserve existing saved
user/tool work on failure; never fabricate an assistant reply.

A03 owns the compatibility `/api/chat` adapter: create when its ID is absent,
otherwise select that ID, ignore client `history` for context/authorization, and
delegate to this one service. B06 completes send; this slice adds no compatibility
route, key loader or alternate session/history store.
